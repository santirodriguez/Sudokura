# Sudokura v1.1.0 implementation brief

This branch is the working branch for the complete v1.1.0 upgrade. Implement the work in this document in one coherent pull request. Do not create a release tag.

## Current-state audit

- The program is a lightweight C + SDL2 + SDL2_ttf application concentrated in `sudokura_sdl.c`.
- The current layout is not reliably responsive. `compute_layout()` forces a minimum board size even when it does not fit.
- `compute_sidebar_rects()` places nine action buttons and nine palette buttons in vertical rows, so controls exceed common window heights.
- Rendering and click handling partly duplicate geometry, especially outside the game screen.
- There is no automated test suite protecting Sudoku generation, game behavior, or layout geometry.
- Visible strings and version text are hardcoded in English throughout the source.
- The macOS workflow links against Homebrew libraries and zips only a bare executable, so the artifact is not a self-contained macOS application.
- Linux uses a generated placeholder icon instead of the supplied artwork.
- Windows packaging needs explicit dependency validation and a real application icon.

## Required implementation

### 1. Build structure and tests

- Add a small, understandable build system. `make`, `make test`, and `make clean` must work on Linux CI.
- Keep the application lightweight and in C.
- Refactor only enough to make core logic and geometry testable.
- Add deterministic tests for:
  - solved-board validity;
  - puzzle uniqueness;
  - clue count and fixed cells;
  - placement and clearing;
  - notes;
  - hints;
  - conflicts;
  - solved-state detection;
  - Classic, Strikes, and Time Attack end conditions;
  - layout bounds and non-overlap.
- Run representative randomized generation tests with fixed seeds.
- Centralize version `1.1.0`.

### 2. Compact responsive interface

Preserve the existing colors, themes, board style, controls, modes, and overall visual identity.

- Replace the tall sidebar arrangement with a compact layout.
- Use a 3×3 numeric palette.
- Arrange action buttons in a compact grid when needed.
- Keep drawing and hit-testing on one shared geometry model.
- Set a realistic minimum window size using SDL.
- Ensure the board and every visible control fit without scrolling.
- Adapt title, help, about, confirmation, and result screens as well as the play screen.
- Validate at least these viewports:
  - 640×480;
  - 800×600;
  - 1024×720;
  - 1280×720;
  - 1366×768;
  - 1920×1080.
- Add geometry tests proving all interactive rectangles are within bounds and do not overlap incorrectly.
- Guard all cell/subcell calculations against zero or invalid dimensions.

### 3. Localization

Add an internal translation system without adding a heavy dependency.

Languages:

- English
- Español — natural Argentine Spanish, displayed as `Español`
- Català

Requirements:

- Add a visible language selector.
- Translate menus, game modes, HUD, buttons, help, about, dialogs, errors, results, and toast messages.
- Keep keyboard shortcuts understandable in all languages.
- Avoid user-visible string literals outside the translation layer, except format fragments that cannot reasonably be centralized.
- Keep UTF-8 and ensure the bundled font supports required accented characters.

### 4. Branding

Original artwork is stored under `assets/branding/source/` and must remain unchanged.

Use:

- `Sudokura03.png`: README and release presentation.
- `Sudokura02.png`: compact in-app horizontal branding where it fits without obscuring the game.
- `Sudokura05.png`: source for application icons.

Create a reproducible script that:

- removes only near-invisible stray alpha pixels;
- crops to meaningful content;
- adds consistent transparent padding;
- centers the icon on a square canvas;
- generates PNG sizes 16, 32, 48, 64, 128, 256, 512, and 1024;
- generates a multi-size Windows ICO;
- generates macOS ICNS;
- generates a small embedded RGBA C resource for `SDL_SetWindowIcon` without SDL_image;
- optimizes generated PNG files without destructive quality loss.

Do not package all original artwork in runtime distributions.

### 5. CI and desktop packages

Add normal CI for pushes and pull requests, then replace the current release workflow with reproducible v1.1.0 packaging.

Linux:

- Build and test.
- Produce an AppImage with the real icon and correct desktop entry.
- Verify the output is executable and report size.

Windows:

- Build a portable ZIP.
- Embed the ICO in the executable.
- Include required SDL2/SDL2_ttf runtime DLLs and transitive non-system DLLs.
- Include one fallback font.
- Validate dependencies before zipping and report size.

macOS:

- Produce `Sudokura.app`, not a bare executable.
- Include `Contents/MacOS`, `Contents/Frameworks`, `Contents/Resources`, `Info.plist`, icon, and fallback font.
- Bundle SDL2 and SDL2_ttf.
- Correct install names and rpaths.
- Fail CI if `otool -L` shows Homebrew or runner-local paths such as `/opt/homebrew` or `/usr/local`.
- Prefer separate arm64 and x86_64 artifacts when practical.
- Clearly mark builds unsigned unless actual signing credentials are configured.

Release workflow:

- Trigger only from `v1.*` tags or manual dispatch as appropriate.
- Generate SHA-256 checksums.
- Create or update a draft GitHub release, never an immediately public final release.
- Use consistent v1.1.0 artifact names.

### 6. Documentation

Update README to reflect the actual build and package behavior.

- Present the new branding without overwhelming the page.
- Document the three languages.
- Document supported controls and compact resizing behavior.
- Correct macOS installation notes.
- Add release notes for v1.1.0.
- State that Android and iOS are a later feasibility phase; do not create mobile projects in this PR.

## Non-goals

- No language or framework migration.
- No gameplay redesign.
- No new game modes.
- No Android or iOS implementation in v1.1.0.
- No signing/notarization claims without credentials and successful execution.
- No release tag or public release from this branch.

## Acceptance criteria

The pull request is complete only when:

1. Existing gameplay features still work.
2. Build and automated tests pass with no important warnings.
3. Geometry tests pass for every listed viewport.
4. English, Español, and Català are complete.
5. Source artwork remains unchanged and derived assets are reproducible.
6. Linux, Windows, and macOS workflows produce self-contained artifacts.
7. macOS validation proves no Homebrew/runner-local dynamic paths remain.
8. Artifact contents and sizes are printed in CI.
9. README and v1.1.0 release notes match actual behavior.
10. The final report lists commands run, results, artifact sizes, and any manual checks still required.
