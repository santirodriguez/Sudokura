# Sudokura v1.2.0 implementation record

This document records the implemented v1.2.0 architecture and validation design. The user-facing summary lives in [`RELEASE_NOTES_1.2.0.md`](RELEASE_NOTES_1.2.0.md).

## Gameplay core

- The application remains C11 with SDL2, SDL2_ttf, and the deliberately approved SDL2_mixer audio layer.
- Generator revision 2 uses a fixed-width deterministic PRNG and deterministic randomized backtracking from an empty board rather than permuting one canonical completed grid.
- Easy, Medium, and Hard generation is deterministic by seed, difficulty, and generator revision.
- Clue removal retains only uniquely solvable puzzles, deterministic scoring separates the supported difficulty bands, and generation never falls back to an 81-clue completed board.
- New normal games obtain their 64-bit seed from operating-system entropy where available, with a deterministic-safe fallback path for environments where that call is unavailable. The generator accepts `2^64` seed values per difficulty; this is an input-space statement and not a uniqueness claim for every final puzzle.
- Daily Puzzle maps a validated Gregorian date to a deterministic seed and uses Classic · Medium for v1.2.
- `game_mode_reveals_correctness()` is the single policy boundary for hidden-solution feedback. Classic and Daily expose fill progress and Sudoku-rule conflicts without revealing whether an otherwise legal entry matches the hidden solution; Strikes and Time Attack retain correctness feedback.
- Hinted cells are locked, and normal input, notes, clear, and Strict-mode rejection flow through one central player-input API.
- Restart restores the exact initial puzzle and clears player progress, notes, and hint markers without changing puzzle identity.

## Session persistence

- Session state and preferences are persisted independently.
- The session binary format is explicitly versioned and serialized field-by-field rather than writing raw C structs.
- Stored session payloads use CRC32 plus semantic validation of board state, generator metadata, ranges, hints, fixed cells, notes, Daily identity, and result state.
- Corrupt or tampered saves fail closed and may be quarantined. A structurally valid save created by an incompatible generator revision is reported as incompatible instead of being mislabeled corrupt.
- Writes use a temporary file followed by replacement so an interrupted write does not intentionally overwrite the last valid state.
- Continue restores the active puzzle, player state, mode, difficulty, selection, timer, mistakes, and pause state.
- Preferences persist language, theme, Strict/Free, last mode, last difficulty, and audio enabled/disabled state.
- The audio preference extension remains backward compatible with the earlier five-byte v1.2 release-candidate preference payload; legacy preferences load with audio enabled and are written in the extended format on the next save.

## Timer and pause model

- Elapsed gameplay time is accumulated using a monotonic runtime clock.
- Independent pause reasons cover manual pause, focus loss, modal screens, Home, and end state.
- Losing focus pauses and autosaves; restoring focus removes only the focus-related pause reason.
- Help and About suspend active gameplay time without incorrectly overriding an existing manual pause.
- Manual pause hides the board and blocks gameplay input until Resume.
- Background audio is paused for manual and focus pauses and resumes only when those audio-pause conditions are cleared.

## Audio

- SDL2_mixer is optional at runtime: failure to initialize the audio subsystem, open an audio device, locate a media file, or decode an OGG never prevents Sudokura from starting or preserving game state.
- The four bundled OGG files are MintoDog's `Cozy Puzzle Jingle & Result` tracks from OpenGameArt under CC0. Exact provenance and the Clear/Failure-to-runtime filename mapping live in `assets/audio/README.md`.
- `music-main.ogg` is the normal loop. Win and loss result jingles interrupt music briefly; the loss screen transitions to `music-fail.ogg` after its jingle.
- Sound can be toggled with `V` or the in-game Sound control, and the preference persists.
- Button/input effects are synthesized in memory as short PCM envelopes and loaded into SDL2_mixer without additional media assets.
- Input cues obey the correctness-visibility policy: Classic/Daily correct and incorrect entries receive the same neutral cue; Strikes/Time Attack may use positive and negative cues; Strict rejection/locked actions use a quiet blocked cue.

## Responsive interface

- Home exposes segmented mode and difficulty selectors plus New Game, Continue, and Daily Puzzle.
- Language selection uses bundled USA, Argentina, and Senyera assets rendered directly from generated RGBA data; SDL_image is not required.
- The game HUD exposes mode or Daily identity, difficulty, time, errors, Strict/Free state, and mode-specific status.
- Progress is graphical, completed number-palette entries are visually reduced, and hinted cells have a distinct visual state.
- Portrait layouts use a horizontal 1–9 number palette while desktop layouts retain the compact grid treatment.
- Regular desktop behavior is retained through 1366×768. At 1600×900 and larger, the XL tier permits a larger shell, board, sidebar, typography, Home, Pause, Result, Help, and About composition. A 1920×1080 layout uses a 900-pixel board; 2560×1440 and 3440×1440 can use a 1080-pixel board while keeping the composition centered rather than stretching controls across the full display.
- Help and About use centered bounded reading widths instead of expanding text across an ultrawide screen.
- The About screen uses existing branding only and presents version, concise project context, `2^64` seed-space information, stack/license, music credit, and direct profile/repository/website links through `SDL_OpenURL()`.
- Buttons, segmented controls, result/pause controls, Back, action buttons, and number palette provide subtle pressed-depth feedback while preserving the established visual style.
- The same geometry structures drive drawing and pointer hit-testing.
- Supported layout tests include desktop sizes from 640×480 to 3440×1440 and portrait sizes 360×640, 390×844, and 412×915.

## Localization and branding

- User-visible interface text is routed through translation tables for English, Español, and Català.
- Maintained Spanish strings use general Spanish forms.
- About content, seed/stack/music metadata, link labels, and link-open failure messaging are localized.
- `sudokura-head.png` is the primary project and in-app identity.
- Source branding variants are preserved under `assets/branding/source/` and `assets/branding/source-packed/`; previous v1.1 artwork is retained under `assets/branding/history/v1.1/`.
- Language flags and their upstream MIT provenance are vendored under `assets/flags/` for fully offline runtime use.
- Derived platform icons, the SDL window icon, embedded head, and embedded flags are generated reproducibly without SDL_image.

## Version and package metadata

- `version.h` numeric major/minor/patch macros are the repository source of truth for v1.2.0.
- `scripts/version.sh` exposes that source version to packaging and CI.
- Package scripts reject an externally supplied version that disagrees with the source.
- Windows version resources use the numeric source macros and string version.
- The macOS bundle renders its Info.plist version fields from the source version during packaging.

## Desktop packages

### Linux

- Portable x86_64 AppImage with application icon, DejaVu Sans fallback font, SDL2_mixer dependency closure, the four OGG resources, and the font license.
- Raw AppDir binary and final AppImage receive smoke tests.
- Package inventory, dependency report, checksum, and size are generated.
- The `linuxdeploy` executable is fetched by an immutable GitHub release asset ID and verified against the upstream-published SHA-256 before use.

### Windows

- Portable x86_64 ZIP with a GUI executable, embedded icon/version resource, fallback font, SDL2_mixer and its required non-system DLLs, and the four OGG resources.
- Recursive PE import closure copies required non-system DLLs and independently rejects unresolved direct imports.
- The packaged directory and extracted ZIP receive smoke tests with a clean runtime search path.
- Archive integrity, resource presence, inventory, dependency reports, checksum, and size are validated.

### macOS

- Separate unsigned x86_64 and arm64 ZIPs containing real `Sudokura.app` bundles.
- SDL2, SDL2_ttf, SDL2_mixer, transitive non-system dylibs, icon, fallback font, audio resources, and font license are bundled.
- Dynamic-library install names use bundle-relative paths; validation rejects Homebrew and runner-local paths.
- Source-derived bundle version, architecture, resources, dependency closure, ZIP integrity, checksum, inventory, and headless smoke-test result are recorded.
- A real Mac launch remains a manual validation gate unless it is actually performed and reported.

## Automated validation

- Deterministic generator revision 2 behavior, 1,200-seed stress coverage, uniqueness, difficulties, Daily identity, Restart, progress, hints, input behavior, conflicts, game-mode endings, localization, and responsive geometry are covered by the core suite.
- Persistence tests cover round trips, corruption, truncation, bad checksums, unsupported format versions, incompatible generator revisions, invalid semantic state, atomic replacement, Daily metadata, result states, and legacy/new preference payloads.
- Seed tests exercise the platform entropy abstraction.
- SDL_ttf tests measure interface text in English, Español, and Català for supported responsive tiers, including wrapped Help/About copy, About metadata, and About link labels.
- SDL2_mixer tests open the real OGG assets with the dummy audio driver and exercise normal/failure contexts, result jingles, all generated UI/input effects, mute, pause/resume, and clean shutdown.
- Linux CI additionally runs AddressSanitizer and UndefinedBehaviorSanitizer against core and persistence tests.
- Diagnostic UI review renders cover ten viewports and six screens, producing **60 non-canonical BMP frames** for Home, Play, Help, About, Result, and Pause. Validation checks exact dimensions and rejects missing or blank-looking frames.
- Linux, Windows, Intel macOS, and Apple Silicon macOS package previews are built before release publication.

## Release process

- Package previews are non-publishing and use the exact requested ref or pull-request head SHA.
- Release automation accepts tags matching `v*` but rejects a tag whose value does not match the version declared by the source.
- The workflow builds four runtime packages plus one combined `SHA256SUMS.txt`.
- Only the draft-release job receives `contents: write`; build jobs use read-only repository permissions.
- A matching release tag creates a draft release for manual review. Publishing the draft remains a separate explicit action.
- The canonical v1.2 screenshot is intentionally deferred until the final release candidate has been manually tested and the user supplies the final image.

## Out of scope for v1.2.0

- Browser/WebAssembly packaging.
- Framework or language migration.
- Online accounts or network-backed puzzle services.
- Signed or notarized macOS distribution unless those steps are explicitly added and actually performed.
