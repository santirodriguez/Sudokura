# Sudokura v1.3.0 implementation record

This file records durable implementation architecture that is useful outside the
temporary execution log. The exact v1.3.0 blueprint and block-by-block execution
state remain in the project continuity record while development is active.

## Phase 1 application-cycle architecture

The Phase 1 boundary deliberately keeps the existing C11 + SDL2 design. It
removes ambiguous active paths without introducing a framework or rewriting the
presentation layer.

| Module | Responsibility |
| --- | --- |
| `game.c/.h` | Sudoku rules, deterministic puzzle identity, cell mutation primitives, conflicts, mode policy and terminal predicates. |
| `app.c/.h` | Canonical application state, semantic gameplay/navigation actions, action outcomes and terminal-state ordering. SDL-independent. |
| `app_clock.c/.h` | 64-bit elapsed-time accumulation and idempotent independent pause reasons. SDL-independent and timestamp-injectable in tests. |
| `session.c/.h` | Versioned session/preferences encoding and semantic validation. |
| `storage.h` | Phase 1 save-operation seam retained for application unit tests. Runtime profile persistence is owned by `profile.c` + `store_io.c`. |
| `input.c/.h` | Physical digit normalization plus keyboard-repeat and mouse-button policy. |
| `progress.c/.h` | Meaningful-progress and Continue predicates. |
| `geometry.c/.h` | Validated base geometry primitives. |
| `audio.c/.h` | SDL2_mixer audio subsystem and policy API used by the SDL shell. |
| `sudokura_sdl.c` + `src/sudokura_sdl/*.inc` | SDL platform/presentation shell. Core/runtime modules are linked as normal C translation units; the remaining UI fragments have an explicit composition order and no macro-renamed alternate render path. |

### Active SDL presentation path

The active frame pipeline is explicit:

1. `app_render_base` clears/paints the board, HUD, Help, Result and Pause surfaces.
2. `app_render_polish` owns Home, About, the compact play identity and number palette.
3. `about_redraw_desktop_cards` is a measured-text helper called by the About renderer, not a second screen route.
4. `app_render_ui` adds the single active gameplay action-control set and Settings panel.
5. `app_frame` synchronizes audio, invokes `app_render_ui` and presents the renderer.

The old base Home/About implementations, duplicate gameplay action controls,
macro render aliases, C-source includes and runtime-only progress precheck were
removed. UI fragments remain internal to one SDL translation unit for now so
Phase 1 does not force an unrelated screen-framework rewrite.

## Input and terminal policies

- Mouse and keyboard gameplay mutations converge on `app_apply_action`.
- A repeated identical value is `GAME_INPUT_NO_CHANGE`: no additional error,
  strike, placement sound or placement save.
- Automatic key repeat is accepted only for continuous selection movement.
  Digits, toggles, F1/F2, pause, mute and other actions execute once per physical
  key press.
- UI controls activate only with the primary mouse button. The secondary button
  is reserved for adding/removing notes through the documented board gesture.
- F1/F2 are global Help/About actions across Home, Play, Pause, Result and the
  auxiliary screens. Settings switches to Help/About without leaking the same
  key event to the hidden play screen.
- Terminality is checked before accepting each event and after every semantic
  action. Loss takes precedence if a state is simultaneously solved and beyond
  a mode limit. A terminal session rejects later gameplay mutations.
- Time Attack expires at the exact configured limit, before accepting a new
  move.

## Clock and focus policy

- SDL supplies platform time only through `SDL_GetTicks64()`; clock semantics
  live in `app_clock.c`.
- Manual, focus, modal, Home and end pauses are independent bit reasons.
  Re-applying an existing reason and removing a reason that is absent are
  idempotent and do not modify accumulated time.
- Help/About/Settings add/remove the modal reason without clearing a pre-existing
  manual/focus pause.
- Losing focus, hiding or minimizing the window adds the focus pause. The board
  is hidden whenever a user-visible manual/focus pause is active.
- Focus recovery does not silently resume gameplay. The player explicitly uses
  Resume; this policy applies consistently to every mode and prevents inspection
  of a Time Attack puzzle while its clock is stopped.


## Phase 2 profile and storage architecture

Phase 2 replaces the three active v1.2 persistence files with one explicit
v1.3 profile container while keeping the v1.2 readers available only for
migration. The legacy files are never rewritten as v1.3 data.

| Module | Responsibility |
| --- | --- |
| `profile.c/.h` | Versioned v1.3 profile schema, normal/Daily slots, unified preferences, bounded future undo/redo and local-result fields, validation and one-time v1.2 migration. |
| `store_io.c/.h` | UTF-8 filesystem boundary, unique temporary writes, flush/sync, same-volume replacement, previous-copy backup and OS writer locking. |
| `store_status.h` | Shared `OK / NOT_FOUND / CORRUPT / INCOMPATIBLE / IO_ERROR` result contract. |
| `session.c/.h` | v1.2 session/preferences reader and serializer retained for compatibility/migration, plus canonical session validation used by v1.3 slots. |

### Format and bounds

The active file is `profile.dat`. Its format separates:

- container version;
- profile-content version;
- preferences-content version;
- per-slot session-content version;
- puzzle generator revision.

The container records an explicit payload length and CRC32. Fields are encoded
one by one; native C structs are never written as an interchange format.
Current bounds include 64 undo entries, 64 redo entries, 128 local results,
counter limits, window-dimension limits and a one-year maximum serialized
session elapsed time. Validation happens before any bounded section is consumed.

The profile has independent **normal** and **Daily** slots. Each slot stores the
puzzle identity, board, notes, mode, selection, timer, result and assisted-game
state. The undo/redo and local-result fields are serialized now so Phase 4 can
activate them without another container migration.

Unified preferences contain language, theme, Strict/Free default, mode,
difficulty, audio enabled state, Music volume, FX volume, reduced-motion state
and window position/size/maximized state.

### Recoverable write policy

Every profile write uses a unique temporary file in the destination directory,
flushes and synchronizes it, and then replaces the active file in the same
volume. Before replacement, the previous active profile is atomically copied to
the single retained `profile.dat.bak`. This provides a recoverable previous
copy; it is not claimed to make arbitrary hardware/power-loss scenarios
impossible.

On Windows the storage boundary converts UTF-8 paths to UTF-16 and uses wide
Win32/CRT APIs for query, open/create, delete and replacement. POSIX uses normal
UTF-8 paths and synchronizes the parent directory after replacement.

A real OS-held writer lock on `profile.lock` prevents a second process from
opening the same profile for writing. A leftover lock file by itself does not
block startup; ownership is the live OS lock and is released when the process
closes.

### v1.2 migration

When `profile.dat` does not yet exist, each existing v1.2 input is first copied
once to a clearly named immutable migration source:

- `session.dat.v1.2.bak`;
- `preferences.dat.v1.2.bak`;
- `audio-levels.dat.v1.2.bak`.

Migration reads those copies, not the mutable originals, creates `profile.dat`,
loads it again and compares the serialized model before activation. The original
v1.2 files are left untouched. A future/incompatible v1.2 session or v1.3
profile is reported as `INCOMPATIBLE` and is never quarantined, deleted or
replaced. Corrupt migration inputs fail closed instead of silently becoming
defaults.

The old audio text file is migration-only. Runtime audio enabled/Music/FX state
now uses the unified profile preferences.

### Live-state authority, checkpoints and save failure UX

The in-memory profile is authoritative while the application is running. A
gameplay mutation updates the appropriate live normal/Daily slot before any disk
write is attempted. If persistence fails, the live slot is retained unchanged
and Continue/Daily resume reads that current in-memory state rather than
resurrecting the last disk checkpoint.

`SavePolicy` groups short bursts of changes for 750 ms. During active,
unpaused gameplay a session checkpoint is attempted at least every 5 seconds;
pause, focus loss, Home, auxiliary-screen transitions and terminal results force
an immediate checkpoint attempt. Therefore the application-level target for an
unexpected process termination is at most 5 seconds of session/timer state since
the previous checkpoint attempt. This is an application checkpoint bound, not a
claim that arbitrary hardware or filesystem failures cannot lose data.

After a save error, a persistent in-app banner explains that the latest progress
remains in memory and exposes Retry. Automatic retries back off instead of
writing every frame. Exit and any operation that replaces a dirty game use an
explicit Back / Retry save / Discard decision. Discard permits the requested
destructive action without pretending the failed write succeeded.

Loads, v1.2 migration and first identity creation use canonical puzzle
validation. Trusted in-process changes use a local invariant validator so normal
keystrokes do not regenerate the puzzle merely to stage a save; the next load
still performs canonical validation.

If the active v1.3 profile is corrupt and `profile.dat.bak` is canonically
valid, startup offers recovery and states that it restores an earlier saved
state rather than starting a new game. Recovery rewrites the active profile from
that validated previous copy without replacing the good backup with the damaged
active file. An incompatible/future profile is never offered destructive
recovery and remains untouched.

### Phase 2 validation boundary

Automated storage tests cover CRC corruption, truncation, future container
versions, semantic bounds, permission/open/write/no-space/sync/replace failures,
previous-copy preservation, live-state preservation across a failed write and
subsequent retry, independent normal/Daily slots, one-time migration, and UTF-8
paths containing non-ASCII characters both beside the test executable and in a
profile-style subdirectory.

The v1.2 fixture matrix covers active, paused, won and lost normal sessions plus
Daily state, with preferences and Music/FX volumes. It verifies preservation of
the complete board/notes/seed identity, timer, pause state and slot type.

Writer exclusion is exercised with a real second process, including unexpected
process exit and subsequent lock reacquisition. A separate child process also
terminates after synchronizing a temporary but before active-file replacement;
the active and previous valid copies must survive and a later write must still
succeed. Linux additionally runs the save policy/profile/live-save regressions
under ASan/UBSan; Windows package CI executes the storage/profile/process tests
through MinGW.

Native Windows acceptance under a real user account whose profile path contains
characters outside the local legacy code page remains an explicit Phase 8.2
native-machine acceptance item. CI does validate non-ASCII UTF-8 paths and the
wide Win32 storage path, but that is not recorded as a substitute for the later
native acceptance.


## Phase 3 human difficulty and generator identity

Phase 3 separates mathematical uniqueness, visible human reasoning, explainable
assistance and generator identity. The classifier remains deterministic and
solution-blind while finding deductions; the closure gate below validates its
outputs independently and records the limits of the human calibration evidence.

### Human evaluator

`human.c/.h` receives only the visible puzzle. It does not receive or read the
hidden solution while searching for deductions. It maintains candidate masks and
applies techniques in a stable order:

1. naked single;
2. hidden single;
3. locked candidate (pointing/claiming);
4. naked pair;
5. naked triple;
6. X-Wing.

Each deduction can report its technique, unit, source cells, affected cells,
candidate/value mask, placement when applicable, and a concise explanation.
The full evaluation records maximum technique, technique-step distribution,
placements, elimination steps and the longest elimination run.

The initial labels are deliberately rule-based rather than clue-score labels:

- **Easy:** solved using naked/hidden singles only.
- **Medium:** solved through locked candidates and actually requires at least
  one locked-candidate elimination.
- **Hard:** requires a naked pair or a supported harder technique (naked triple
  or X-Wing).

Clue count remains generation data and a search bound; it is not the difficulty
definition. Boundary cases that do not meet the requested human rule are
discarded rather than silently relabeled.

### Generator revisions

Revision 2 remains a frozen compatibility path. Its RNG keys, clue targets,
removal order and exact output are preserved so saved v1.2/v1.3 sessions and
Daily identities can be reconstructed exactly. Canonical session/profile
validation regenerates using the revision stored with the identity.

Revision 3 is the default for newly created puzzles. Identity is the tuple of
generator revision, difficulty and seed (plus frozen local date for Daily).
Uniqueness continues to use the independent solution counter; human difficulty
is evaluated separately.

Revision 3 uses deterministic attempt budgets rather than measured milliseconds:

- Easy: 64 attempts;
- Medium: 256 attempts;
- Hard: 128 attempts.

The fixed 1,000-identity corpus observed maxima of 2, 199 and 84 attempts
respectively. Medium therefore keeps a 256-attempt ceiling rather than the
earlier 192-attempt value that demonstrably exhausted one corpus identity.
Hard is capped at 128 rather than carrying an unnecessarily large tail budget.

A candidate is published only when it is unique and matches the requested human
rating. Exhaustion returns an explicit generation failure and never returns a
complete-board fallback or a puzzle with another difficulty label. Normal-game
Retry requests a fresh random identity. Daily keeps its frozen date/revision
identity and reports failure instead of silently changing that identity.

The SDL shell displays generation state and progress, pumps platform events
during the deterministic search and supports Escape cancellation. Generation
builds into a temporary `Game` and publishes it only after a complete valid
result, so cancellation/exhaustion leaves the currently displayed game intact.
The algorithm does not make board decisions from wall-clock duration.

### Explainable Hint and assisted-state policy

Hint now opens a non-modal explanation instead of immediately revealing a
solution cell. It identifies the supported technique, source/affected cells and
candidate digits with shape-coded markers as well as color, then lets the player
apply the resulting logical placement. EN/ES/CA copy names the technique and
explains the target. A visible contradiction is marked directly. A state that
cannot safely accept the proposed logical placement is not mutated; the player
is offered explicit Verify instead.

Reveal selected remains a distinct labeled action. Apply, Verify and Reveal
mark the session Assisted because they apply or expose information; merely
opening/canceling a Hint preview does not. Verify checks current filled entries
without changing the board or adding the existing mistake/strike penalties.
Reveal keeps the existing reveal behavior and no-op protections for fixed,
already-resolved or otherwise unchanged cells.

### Phase 3 validation boundary

The quality gate fixes 1,000 revision-3 identities per difficulty. For every
generated puzzle it independently proves uniqueness with a separate DFS solver,
checks the requested human label, observes every evaluator placement/elimination
and rejects any deduction that would remove the independently solved value.
Revision-2 coverage hashes exact boards across extreme seeds and Daily dates and
also exercises restart. The locked corpus digests are:

- revision 2 compatibility corpus: `5072a1de5f9435df`;
- revision 3 Easy: `5ccc476e403d0761`;
- revision 3 Medium: `1cfda8df90ebfdb3`;
- revision 3 Hard: `3f3e198efc172cd1`.

The same digests were produced on Linux and Windows CI. On the identified Linux
reference runner (AMD EPYC 9V74 80-Core Processor), generation wall time for
Easy/Medium/Hard was respectively median 1.360/144.632/222.963 ms, p95
1.467/619.566/1049.935 ms and maximum 4.381/1420.846/2809.642 ms. The usual
median remains below the 250 ms design target on that reference runner; slower
tail cases remain cancellable and keep the UI event pump active instead of
weakening uniqueness or the requested difficulty.

Human calibration uses the pinned CC0
`tests/fixtures/human_difficulty_20240415.csv` fixture from Sheng-Wei Wang's
2024 human-player dataset (upstream blob
`61518b820af3a488d5359f790d3c6b2455313acd`). Of 344 records, the supported
classifier solved 320 as Easy, 9 as Medium and 1 as Hard, with 14 unsupported.
The median human metrics rise clearly from Easy to Medium
(`D_TO` 0.7973 -> 1.2953; `D_TR` 1.2334 -> 4.4248), which is enforced as a
calibration regression. The single supported Hard record is too small a sample
for a defensible human ordering claim, so Hard remains rule/corpus validated
rather than being presented as objectively calibrated by that dataset.

Phase 3 therefore closes H15/H16 at the product/automated-evidence level while
retaining the explicit limitation above: the labels are engineered,
human-reasoning tiers, not universal objective difficulty measurements. H27's
new-generator unbounded attempt path remains eliminated by deterministic
budgets; the broader persistence-cost work stays with its later phase owner.


## Phase 4 player tools and reversible notes

Phase 4 Block A implements bounded, persistent correction tools without
changing puzzle identity or weakening the existing mode semantics.

### Reversible edit model

Player edits use a bounded 64-entry Undo stack and a bounded 64-entry Redo
stack per normal/Daily slot. The bound reuses the capacity reserved in the
Phase 2 profile model rather than enlarging the profile format solely to match
the blueprint's illustrative 200-action proposal.

Each history entry is a compound `GameEdit`. It records the selected cell's
value, notes and hinted state before/after the action plus the placed digit and
a compact mask for any related notes removed from visible row/column/box peers.
Therefore placing a digit and cleaning matching peer notes is one reversible
action.

Undo/Redo is board-history only. It does not restore elapsed time, mistakes,
strikes, other penalties or clear the Assisted condition. The actions are
blocked once the game is terminal. A new edit after Undo discards the Redo
branch. Restart clears both history stacks while preserving the exact puzzle
identity.

### Note policy

Manual notes remain explicit. Repeating the current placed value is a no-op and
does not erase incidental state. Replacing/clearing a value records the selected
cell's previous notes so the operation can be reversed exactly.

Automatic peer-note cleanup is an opt-in persisted preference, default OFF. When
enabled, a placed digit removes that same note only from editable empty cells in
the visibly related row, column and box. It never reads the hidden solution.
The cleanup is stored in the same compound history entry and is restored by
Undo.

Candidate auto-completion is intentionally not added in Block A. Its
contradiction/replacement-confirmation UX would broaden the change into work
owned by later interaction/design phases.

### Persistence compatibility

Profile preference content advances from version 1 to 2 and session content
from version 2 to 3. Readers for the previous versions remain supported.
Version-3 history entries add the compound peer-note metadata; older entries
decode with that metadata empty. Profile validation checks both edit bounds and
that the recorded Undo/Redo chains can be applied reversibly from the saved
board.

### Player controls

Delete/Backspace continues to clear the selected editable cell. A visible
localized Clear/Borrar/Esborra control shares the existing responsive Restart
control area rather than adding a new action row that would reduce the minimum
360x640 board geometry.

Ctrl+Z performs Undo; Ctrl+Y and Ctrl+Shift+Z perform Redo in this Block A
implementation. Platform-specific shortcut presentation and complete
mouse/keyboard parity remain part of Phase 4.4. Shift+N toggles the persisted
automatic peer-note cleanup preference.

### Phase 4 Block A validation boundary

Focused regressions cover compound peer-note reversal, bounded history,
Undo/Redo sequencing, Redo truncation, Restart history reset, preservation of
penalties/Assisted state, terminal blocking and persisted compound edit
round-trip. The full existing CI matrix remains the acceptance gate for
warnings-as-errors, functional/UI tests, sanitizers, build and Windows package
smoke.


### Continuity, Daily and local results

Phase 4 Block B activates the independent normal/Daily slots prepared in Phase 2
instead of introducing a parallel continuation model. Home derives resume
metadata directly from those slots and presents normal and Daily continuation
independently. A normal continuation includes its mode, difficulty and elapsed
time. A Daily continuation includes its date, difficulty and elapsed time.
Creating a new normal game only replaces the normal slot.

An active saved Daily remains resumable even after the local date changes. A
completed Daily remains stored in the Daily slot for its date while normal play
continues. Selecting Daily on Home resumes an active saved Daily first; otherwise
today's deterministic Daily identity is used.

Terminal outcomes are recorded in the existing bounded 128-entry local result
history. Recording is idempotent for the complete terminal event identity, so
reopening a completed slot, repeated terminal handling and repeated saves do not
increment result history again. When the history is full, the oldest result is
discarded.

The local summary intentionally remains small. Finished counts are grouped by
mode/difficulty. Best winning time is shown only when mode, difficulty,
generator revision, normal-vs-Daily identity class and Assisted condition are
equivalent. This prevents incomparable rule/revision runs from being presented
as one personal best. No rankings, streaks or achievement system are added.

The result screen is mode-aware: Classic/Daily do not show a meaningless
zero-error counter; Strikes shows strikes; Time Attack may show its error count.
Elapsed time and used hints remain visible, and Assisted is explicit when
applicable. The actions are semantically distinct: a win offers another game
(or explicitly another normal game after a Daily), a loss offers retry of the
same board, and the secondary action returns Home. A completed Daily is never
described as if a normal game were the next Daily.

### Unified input contract

Top-row digits and the numeric keypad feed the same digit mapping. Left-click is
the only primary UI activation button. Right-click is reserved for writing a
note in the clicked editable board cell and cannot activate language, Home,
result, pause, confirmation, sidebar or information controls.

The responsive play-control rectangles remain the geometry authority. Existing
rows are split consistently for render and hit testing: Menu/Pause, Undo/Redo
and Restart/Clear. This exposes all correction/navigation actions to mouse users
without adding a row that would reduce the 360x640 board allocation.

Undo/Redo/Verify use the platform primary modifier: Ctrl on Windows/Linux and
Cmd on macOS. Help renders that actual modifier rather than promising one
hard-coded shortcut. Delete/Backspace and visible Clear erase the selected
editable cell; N toggles Notes, Shift+digit writes a note, Shift+N toggles
visible-peer note cleanup, P pauses, H opens Hint, and the platform primary
modifier plus Enter invokes Verify.

The Audio panel is also keyboard-operable: Up/Down moves between its Toggle,
Music, FX and Back controls; Left/Right changes Music/FX (or the toggle when
focused); Enter/Space activates Toggle or Back; Escape closes the panel. The
focused Audio control receives the same visible focus treatment used by the
rest of the keyboard UI.

### Phase 4 Block B regression coverage

Focused tests cover:

- idempotent result insertion, the 128-result bound and comparable best-time
  filtering;
- result-history dirty-state persistence;
- Ctrl/Cmd platform shortcut selection;
- responsive text fit for split play controls, independent Home continuation
  labels/details and result actions at every supported geometry tier;
- a full keyboard interaction contract and a full mouse interaction contract,
  each completing a generated puzzle through the same input/action layers used
  by the UI;
- existing profile round trips preserving both normal and Daily slots, persisted
  Undo/Redo compound edits and notes.

The interaction contract deliberately exercises the testable input mapping and
application action layers rather than adding a second synthetic SDL event
framework. Package smoke still launches the real SDL executable under the
platform CI environment, while the input, geometry and action semantics remain
covered by deterministic focused tests.

Phase 4 closure requires the final documentation head to pass the complete
existing Linux/Windows CI matrix: warnings-as-errors tests and UI tests,
generator corpus, ASan/UBSan, full Linux build and Windows package validation.


### Phase 4 hazard closure

The Phase 4 closure hazards are resolved/defined as follows:

- **H09:** visible Clear plus bounded persisted Undo/Redo restore values, notes
  and compound peer-note cleanup without returning penalties/time/Assisted state.
- **H17:** normal and Daily use independent persisted slots and independent Home
  continuation surfaces; replacing normal play does not overwrite Daily state.
- **H21:** play actions now have consistent keyboard/mouse access, native
  Ctrl/Cmd Undo/Redo/Verify shortcuts, and a keyboard-operable Audio panel.
- **H22:** Help now states the actual Classic/Daily neutrality, Strikes loss
  rule, 10:00 Time Attack budget and non-time mistake behavior, Free/Strict
  visible-conflict semantics, explicit Verify/Hint assistance, and Clear
  behavior. Results no longer show meaningless Classic/Daily error zeroes and
  Daily completion no longer labels a following normal game as "Next".

The remaining H21/H22 visual/accessibility polish explicitly owned by Phase 5
may refine presentation, but Phase 4 leaves no undefined player action or
result/continuity semantics.


## Phase 5 Block A — visual system and screen hierarchy

Phase 5.1–5.2 replaces the accumulated presentation overlays with a smaller
responsive visual contract while preserving the Phase 4 gameplay/input
semantics.

### Single geometry and visual metrics

`geometry_compute()` is the sole exported final layout authority. The previous
`ui_geometry.inc` adjustment layer is no longer composed or included by the
geometry/text-fit tests. Rendering and layout-sensitive interaction therefore
consume the same final rectangles that the regression suite validates.

`GeometryStyle` centralizes the small set of presentation metrics needed by
the current renderer: spacing tiers, panel/control radii, minimum supported
control height and minor/major Sudoku grid stroke widths. Larger tiers may use
larger preferred controls, but the global validity contract represents the
smallest supported geometry rather than a desktop preference.

Play now reserves an explicit validated `status` rectangle. Transient player
messages and save-failure/retry feedback use bounded layout space rather than
negative or ad-hoc coordinates above/below the board.

### Board hierarchy and non-color-only states

The Sudoku board remains the dominant surface. Major 3×3 separators are drawn
with physically thicker strokes than cell separators. Same-digit highlighting
adds line markers and conflicts add an X marker, so those states do not depend
only on fill color. Existing hinted-cell markers remain shape-coded.

Secondary navigation was reduced in Play: About and the language selector are
not permanent gameplay chrome. Settings and Help remain explicit player tools;
Menu/Pause, Undo/Redo and Restart/Clear keep the Phase 4 shared responsive
control rectangles.

### Home hierarchy

Home uses one contextual primary action. When a normal game is resumable,
Continue normal game receives initial keyboard focus and the primary visual
treatment; New Game becomes secondary. Without resumable normal progress, New
Game remains the primary action. Daily continuation remains independent and
retains its date/difficulty/time context.

The direct Theme secondary button was replaced by Settings. The `T` shortcut
remains available for compatibility, but preferences no longer compete as
multiple equally prominent Home actions.

### Settings

The existing `APP_SCREEN_SETTINGS` auxiliary screen is the single settings
surface; no second settings architecture or profile migration was introduced.
It exposes the preferences already owned by the profile/runtime:

- Theme;
- Language;
- Sound enable/disable;
- Music volume;
- FX volume;
- Reduced motion;
- Back.

Settings is usable from both Home and Play. Keyboard focus moves with
Tab/Up/Down, Left/Right changes the focused value or slider, Enter/Space
activates applicable controls and Escape returns. Mouse controls use the same
visible rows/sliders.

`reduced_motion` already existed in the persisted preference schema. It is now
loaded into `AppState`, saved with the other UI preferences and suppresses the
victory animation when enabled. Phase 6 still owns DPI/scaling and advanced
window-position behavior; those controls are not pulled forward here.

### Render-pipeline consolidation and text fitting

Settings is now a true auxiliary surface. The base renderer clears the Settings
background instead of repainting the Play board, and the final Play controls
are restricted to `SCR_PLAY`.

About has one active renderer. The former desktop-only
`about_overlay.inc` redraw is no longer included in application composition.
The primary renderer uses measured wrapped fitting for About body/fact/study
copy. Supported geometries are required by `test_text_fit` to fit at or above
the configured minimum font size. If a platform font unexpectedly exceeds those
validated metrics at runtime, the minimum-size wrapped texture is clipped inside
the validated rectangle rather than silently disappearing.

The same text-fit gate now covers the actual Settings labels instead of the
retired Audio-only panel.

### Block A validation boundary

Phase 5 Block A keeps the existing minimum supported matrix, including 640×480
desktop and 360×640 portrait. Focused tests cover final geometry bounds,
responsive text fit across EN/ES/CA, Settings labels, auxiliary-screen
navigation and the persisted reduced-motion preference through the existing
profile round-trip.

The full Linux/Windows CI matrix remains the acceptance gate: warnings-as-errors
tests and UI tests, generator corpus, ASan/UBSan, full Linux build and Windows
package validation. Phase 5.3–5.4 accessibility audit/screenshot-matrix closure
and Phase 6 DPI/window work remain explicitly outside this block.

## Phase 5 Block B — practical accessibility and diagnostic review

Phase 5.3–5.4 closes the practical keyboard/accessibility and visual-review
requirements without claiming formal accessibility certification.

### Focus, activation and escape behavior

Home and Settings retain their existing focus models. Help, About, Result,
user-visible Pause, Hint preview and the visible Play controls now expose a
cyclic keyboard focus. Tab and Shift+Tab move that focus, Enter or Space
activates the focused control, and Escape returns predictably. Direct gameplay
shortcuts remain available and selection arrows/WASD still move the Sudoku cell
selection rather than conflating board navigation with control focus.

Play focus includes Menu/Pause, Undo/Redo, Restart/Clear, Hint, Notes, Verify,
Settings, Help, Free/Strict, the number palette and Retry save when a save error
is visible. Mouse activation updates the corresponding focus where useful, so
keyboard and pointer feedback converge on the same rectangles.

Settings sliders support minus/plus buttons, click-to-position, arrow-key
adjustment and pointer drag. Visible percentages remain the value authority.

### Reduced motion, contrast and language audit

Reduced motion already disabled the victory animation; it now also removes the
non-essential selected-cell pulse while preserving the static selected outline.

The design targets remain 4.5:1 for normal text and 3:1 for functional
structure. `scripts/validate_contrast.py` reads the canonical theme definitions
and enforces those targets. The light fine-grid tone was darkened to meet the
functional-structure target. These are design regressions, not an accessibility
certification.

`tests/test_i18n.c` requires complete non-empty EN/ES/CA coverage, valid UTF-8
and the Help formatting contract. Help copy now explicitly distinguishes visible
row/column/box conflicts from Verify's solution comparison. Text-fit regression
adds proportional 125/150/200-percent review sizes while Phase 6 remains the
owner of actual DPI/coordinate-scaling mechanics.

### Single presentation route

The former `polish_ui.inc` and `rc2_ui.inc` composition layers are retired from
the active build. Their current helpers are consolidated into `ui_present.inc`,
and `app_render_ui()` directly owns the single presentation route: base surface,
screen-specific presentation, then state overlays. This removes the Phase 5
layered-patch dependency without changing gameplay rules.

### Diagnostic screenshot matrix

`--render-screenshots` now emits 78 temporary diagnostic BMPs plus
`MANIFEST.tsv`:

- 12 required states across five representative viewports: Home without save,
  Home with resumable save, notes, visible conflict, Hint, save failure, Pause,
  loss, win, Help, Settings and About;
- the viewport set is 640×480, 1024×768, 1366×768, 360×640 portrait and
  1920×1080 large;
- 18 additional 1024×768 Help/Settings/About frames cover all EN/ES/CA ×
  dark/light combinations.

Each manifest row records state, locale, theme and the visible focus rectangle.
`scripts/validate_screenshots.py` verifies the required state/viewport matrix,
the complete locale/theme audit, exact BMP dimensions, non-blank rendering and
that the focused control remains inside the rendered viewport. Geometry and
text-fit tests remain the machine check for layout/text bounds; the artifact is
also intended for grouped human visual inspection.

Normal CI does not render this heavy matrix on every push. A commit explicitly
tagged `[ui-review]` enables the diagnostic job and uploads the matrix for seven
days. Workflow concurrency cancels superseded runs on the same ref so an older
push does not continue consuming CI after a newer head exists.


### Help overflow correction from visual review

The first Phase 5 review artifact exposed a real portrait defect that pixel-count
validation had not caught: Help at 360×640 showed only the first portion of its
copy. Help now keeps the established readable body font and scrolls only the
body region when necessary. Up/Down, PageUp/PageDown, Home/End and the mouse
wheel move the body; the heading and Back control remain fixed and keyboard
accessible. A visible scrollbar communicates that more content exists.

The screenshot manifest now records Help scroll position/range. The six
EN/ES/CA × dark/light Help audit frames capture the bottom of the text while the
five representative viewport frames capture the top, proving that overflow is
reachable rather than silently clipped. The validator requires every
`help-bottom` audit to have a positive range and to render at its actual end.


## Phase 6 Block A — desktop coordinates and measured work

Phase 6.1–6.2 establishes explicit desktop rendering semantics before any
device-audio work.

### HiDPI and window state

The SDL window requests `SDL_WINDOW_ALLOW_HIGHDPI`. Application geometry,
hit-testing and persisted window dimensions remain in logical window
coordinates. `DesktopMetrics` records the renderer output separately and
derives the physical raster scale. `SDL_RenderSetLogicalSize` keeps draw
coordinates aligned with input while fonts are opened at the physical scale and
their measured dimensions are converted back to logical units. This avoids
treating renderer pixels as window coordinates or multiplying system scale
twice.

Normal restored bounds are retained separately from maximized state. A saved
position is reused only when at least 64 logical pixels intersect a current
display's usable bounds; otherwise the window is centered on an available
display. Resize, move, maximize/restore and display-change events refresh
metrics, while renderer reset events rebuild renderer-owned textures. The
existing preference schema already owned window x/y/width/height/maximized, so
no profile migration is required.

Font resolution is bounded and package-first: explicit `--font`, packaged
font beside the executable (or macOS Resources), explicit development paths,
then a finite set of platform font locations/names. Recursive filesystem font
search is removed.

### Idle rendering and bounded text reuse

The main loop no longer redraws unconditionally. It waits for SDL events with a
bounded timeout, redraws immediately for state/input changes, and refreshes only
while gameplay clocks or non-reduced animations require it. Software-renderer
animation refresh is capped at roughly 30 Hz. Audio ticking and save-policy
timeouts continue while no frame is drawn.

Rendered text uses a bounded 128-entry LRU texture cache keyed by font, exact
UTF-8 content, color, wrapping width and scale-sensitive font identity. Cache
entries are invalidated on language, theme, logical-size or scale changes and
before font/renderer resource rebuilds. Wrapped-text source cropping converts
logical crop rectangles back to physical texture pixels, preserving Help/About
behavior on HiDPI outputs.

### Measurement contract

`--desktop-benchmark` measures startup through first Home frame, median
input-to-render latency, one-second idle CPU usage using the actual Home wait
cadence, Easy/Medium/Hard five-sample p50/max generation costs, median
runtime-profile save cost, and RSS before churn, after cache warm-up and after a
second identical size/theme/language churn where the platform exposes it. The
report also records renderer kind, scale and bounded-cache occupancy.

The conditional `[desktop-benchmark]` CI milestone runs those measurements on
the Linux reference runner and records current/v1.2 `--smoke-test` wall time
and maximum RSS on the same host. Results are uploaded as
`phase6-desktop-benchmark`; they are evidence, not universal performance
promises. Phase 6.4 remains responsible for the final target assessment and
physical cross-platform checks.

No background generation/save thread is added in this block. Generation is
already bounded/cancellable, and same-identity profile writes use runtime
validation rather than canonical puzzle regeneration. Threading remains
unjustified unless the measurements show a player-visible latency problem.


## Phase 7 Block A — package traceability and Windows distribution

Phase 7.1–7.2 moves package identity to v1.3.0 and makes each candidate
self-describing without treating a preview build as a published release.

### Exact source and toolchain traceability

`version.h` is the sole version source. Preview and release workflows first
resolve an explicit ref to one commit and all platform jobs then check out that
immutable commit, avoiding branch movement between package jobs. GitHub Actions
are pinned to concrete commit SHAs. Package scripts emit per-platform build
provenance plus JSON artifact manifests containing source commit, version,
artifact kind, platform/architecture, declared support baseline, SHA-256, byte
size and v1.2 size comparison. The record explicitly avoids a bit-for-bit
reproducibility claim.

The package payloads include the GPLv3 license, DejaVu notice, audio provenance
and common distribution notice. Windows additionally records package
owner/version/license metadata for every bundled MinGW DLL and copies
package-provided license files where available.

Linux candidate packaging also fixes the complete AppImage construction chain:
linuxdeploy `1-alpha-20251107-1`, appimagetool `1.9.1`, and type2-runtime
`20251108` are retrieved as stable GitHub release assets and verified against
their published SHA-256 digests. The runtime is passed explicitly with
`--runtime-file`, so package creation does not silently fetch the mutable
`continuous` runtime. The candidate check also verifies `X-AppImage-Version`
is derived from `version.h`.

### Windows ZIP and per-user installer

The existing x86_64 portable ZIP remains. The same validated `dist` directory
also feeds a small Inno Setup installer. Inno Setup 7.1.0 x64 is downloaded
from its immutable upstream release asset and verified against SHA-256
`0362a383ed217d4c4239b5933866dd96d3eb2102737da92f80f6057a4b40df2f`
before use. The installer requests lowest privileges, installs under the
current user's LocalAppData Programs directory, creates Start-menu access and
offers an optional desktop shortcut.

ZIP extraction and installer installation are exercised from paths containing
spaces, accented text and a character outside a Western legacy code page.
Both forms run the same packaged smoke test. Save/settings data remains owned
by SDL's per-user preference path, so package replacement and uninstall do not
delete the profile. The shipped Windows README documents profile location,
manual deletion, and the truthful unsigned/SmartScreen state without asking
users to disable protections.

Block A is not a release-acceptance claim. Linux cross-distro/FUSE/Wayland and
modern-macOS scope/DMG/Mach-O acceptance remain owned by Phase 7 Block B and
Phase 8.


## Phase 7 Block B — Linux portability and scoped modern macOS

### 7.3 Linux x86_64

The AppImage candidate is built only on an Ubuntu 22.04 runner and fails closed if the build host changes. The package audit walks every bundled ELF, rejects unresolved dependencies and build-host paths, enforces an x86_64 payload and a maximum GLIBC requirement of 2.35, records external system dependencies separately, rejects bundled graphics-driver implementations, and maps bundled shared libraries back to Debian packages with their installed copyright files.

The final AppImage is then exercised outside the build host on Ubuntu 24.04 and Fedora 44. The runtime probe uses a Unicode/space path and foreign working directory, custom XDG roots, the explicit `--appimage-extract-and-run` fallback, a normal FUSE launch on Ubuntu 24.04, an X11 session under Xvfb, and a native SDL Wayland probe under a headless Weston compositor. These are automated portability probes, not claims of GNOME/KDE desktop acceptance; the real GNOME/KDE/Wayland/X11 walkthrough remains Phase 8.

### 7.4 macOS 15+ arm64

The v1.3 candidate stops producing new Intel artifacts. The single Mac target is macOS 15.0+ on Apple Silicon/arm64. `MACOSX_DEPLOYMENT_TARGET` and `LSMinimumSystemVersion` are both 15.0. Every bundled Mach-O is audited for arm64-only architecture, deployment target, dependency/rpath closure and signature validity.

The bundle copies dependency license metadata/material, relocalizes all non-system dylibs first, then applies an ad-hoc integrity signature to nested dylibs, the executable and final app. That signature is explicitly an integrity aid only: it is not Developer ID and not notarization.

Distribution changes from the historical ZIP to a simple DMG containing `Sudokura.app` plus an Applications shortcut. CI verifies the DMG structure, mounted bundle integrity and a headless packaged smoke where the runner permits it. The candidate remains experimental on macOS until Phase 8 opens the downloaded DMG on real hardware with real Gatekeeper/quarantine state, persistence, Retina and audio checks.

The v1.2 arm64 ZIP size is retained only as a contextual reference because DMG-vs-ZIP is not a like-for-like size comparison.
